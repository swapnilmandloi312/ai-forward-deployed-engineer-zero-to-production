# Four worked Muse practice recipes

These are original task designs, not claims that a particular account has every integration enabled. Start in the conversation with synthetic text. Use an external connection only after verifying that the current product supports it for your account.

## 1. Build a research brief that can be checked

**Situation:** you need to compare three tools for parsing documents. Supply the official pages for the exact three candidates and your actual constraints: tables, scans, local operation, license, and expected volume.

```text
Compare these three official project pages for my document-processing task.
Separate documented capability, inferred suitability, and unknowns.
For every important claim, provide the source and section.
End with a small experiment that could disprove your recommendation.
Do not use a vendor benchmark as a prediction of my own workload.
```

**Review:** follow the sources, inspect license scope, and verify whether external models or hosted services introduce costs. **Failure example:** calling a project free because its UI can be downloaded while ignoring a required paid model API. **Improve:** require a cost-dependency column and a synthetic test file.

## 2. Turn a goal into a realistic learning project

**Situation:** a learner knows APIs and wants to understand retrieval. Supply a weekly time allowance and the desired output: a small cited-answer experiment.

```text
Design a four-stage learning project for a beginner who understands Python
functions, HTTP, and basic SQL. Each stage needs an explanation, one build
exercise, an expected artifact, and a question I must answer without notes.
Keep the initial path independent of paid APIs. Mark later optional services.
```

**Review:** can the first stage run at the learner's level? Does every stage produce evidence? **Failure example:** assigning distributed vector infrastructure before the learner understands a chunk. **Improve:** ask for a smaller local baseline and a prerequisite explanation.

## 3. Prepare an honest customer update

**Situation:** extraction works on six synthetic invoices, but ambiguous vendors still need review. The next integration is not implemented.

```text
Draft a short customer update from these facts only:
six synthetic invoices tested; extraction fields are reviewable;
vendor ambiguity remains; accounting integration is planned, not built.
Explain the current result, the limit, the next milestone, and one decision
needed from the customer. Make no accuracy or time-saving claim.
```

**Review:** the draft must not turn six examples into a production accuracy percentage or say the accounting API is connected. **Improve:** ask it to label each sentence as observed, planned, or needing confirmation before finalizing.

## 4. Design a recurring responsibility before enabling it

**Situation:** you want a weekly project review. First write the contract, then use the supported product interface if you choose to enable the task.

Specify the source, time zone, schedule/end condition, output location, missing-data behavior, and interruption rule. Require confirmation of what was actually saved. If scheduling is unavailable, keep the result as a manual checklist; do not claim an active automation.

**Review:** a dated deliverable and a visible saved responsibility are stronger evidence than a conversational promise. **FDE lesson:** activation, execution, and successful delivery are separate states.
